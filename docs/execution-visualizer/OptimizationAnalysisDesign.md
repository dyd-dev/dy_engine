# 최적화 기능별 실행·비용 비교

## 목적과 완료 기준

사용자는 컬링과 컴퓨트를 전체 기능의 예시로 들었다. 원하는 결과는 현재 엔진의 최적화 기능을 켜고 끄면서, 실제 제작물에서 어느 단계의 작업과 비용이 줄거나 늘었는지, 데이터와 명령의 진행 경로가 어떻게 달라졌는지 보는 것이다. 예제 전용 제어나 전체 FPS 표만으로는 완료되지 않는다.

기존 LiveClient, source/revision, 1초 집계, 실제 이벤트 기반 Flow를 확장한다. 예제는 검증용 부하로 사용하며 기능 구현은 해당 엔진 계층에 둔다. 현재 기본 동작은 유지한다. 사용자 정의 제작물에는 해당 엔진 경로에서 실제 등록한 기능만 조작 항목으로 나온다.

분석기 소스와 자체 테스트는 사용자의 폴더 정리 지시에 따라 `src/Extend/ExecutionVisualizer`에 둔다. 외부 라이브러리 연동인 `ImGui`, 자체 확장인 `Model`과 같은 위치다. 별도 최상위 `tools` 폴더는 사용하지 않는다. 제작물에 들어가는 공통 계측은 기존 엔진 계층과 public Diagnostics 계약에 남고, GUI 의존성은 제작물에 들어가지 않는다.

## 비교 화면

1. 기능 목록: 기능의 역할, 적용 조건, 실제 설정, 실행 중 변경 가능 여부를 표시한다. 같은 결과를 만드는 최적화, 화면 결과를 바꾸는 품질 설정, 빌드에서 결정되는 항목을 구분한다.
2. 단계별 영향: CPU 준비, 데이터 준비, 업로드, 명령 기록, native 변환, 제출·대기, GPU, 출력의 이전/이후 1초 값과 변화량을 보여준다. CPU·GPU 시간 외에 처리 개수, 바이트, 명령 수, 생성·해제, 배치, 부분·전체 업로드를 사용한다.
3. 전후 원본 흐름: 각각 실제로 관측한 원본 프레임의 이벤트와 연결을 보존해 나란히 표시한다. 평균 구간과 원본 한 프레임은 서로 다른 증거임을 표시한다. 실제 연결이 없는 화살표를 설명 목적으로 만들어 넣지 않는다.
4. 해석: 해당 기능이 줄이려는 작업, 추가하는 비용, 현재 부하에서 관측된 변화를 연결한다. 관측되지 않은 효과는 효과가 없다고 단정하지 않는다. 여러 설정이나 장면이 함께 바뀌면 한 기능의 효과로 단정하지 않는다.

본문 22px와 넉넉한 간격, 선택 경로 중심의 겹치지 않는 선, 한 원본 경로를 3초 동안 따라가는 표시를 유지한다. 수치는 기존처럼 1초마다 갱신한다. 상세 정보는 펼쳐서 확인하고, 좁은 창에서는 글자를 줄이지 않고 스크롤한다.

## 현재 소스에서 확인한 비교 대상

아래는 구현 상태와 비교 경로 설계를 구분한 목록이다. 새 제어의 완료 상태를 뜻하지 않는다.

|---|---|---|
| Renderer | 인스턴싱 | 기존 개별 Draw 경로. 배치·Draw·binding·CPU 기록 비용 비교 |
| Renderer | 프러스텀 컬링 | 기존 전체 대상 제출 경로. 검사 비용과 제외된 인스턴스·GPU 작업 비교 |
| Renderer | 병렬 RenderGraph 기록 | 기존 직렬 기록 경로. 기록·native 변환·작업 분배 및 대기 비교 |
| Renderer | 변경 transform 구간 업로드 | 같은 인스턴스 버퍼에 전체 transform을 전송. 범위 탐색 비용·전송량·Upload 호출 비교 |
| Renderer | ResourceSet 재사용 | 같은 binding으로 새 ResourceSet 생성. 조회 비용·생성 수·기록 비용 비교 |
| Renderer | bindless 재질 경로 | 기존 일반 재질 경로 사용 가능 여부를 셰이더와 backend 조건에 맞춰 검사. 배치 분할·binding·재질 데이터 비용 비교 |
| Canvas | 인접 draw 병합 | 순서를 유지한 개별 draw. 정점·알파 순서·viewport·scissor는 보존 |
| Canvas | 이미지/ResourceSet 캐시 | 같은 이미지의 새 GPU 자원 준비. 이미지 전송·생성 및 재사용 비용 비교 |
| Canvas | 정점 버퍼 재사용 | 같은 정점 데이터용 버퍼 재생성. 생성·할당과 전송량 구분 |
| Model | VS/Compute 스키닝 | 기존 모드 전환. Compute·barrier·추가 출력 버퍼와 graphics 비용 비교 |
| Model | 완료된 frame-slot 버퍼 재사용 | 완료 확인 후 버퍼 재생성. GPU 완료 보장은 그대로 유지 |
| Model | 동일 바이트 업로드 생략 | 같은 버퍼에 강제 업로드. memcmp 비용과 실제 Upload 비용 비교 |
| Model | 정적 mesh/influence 데이터 재사용 | 같은 검증된 데이터 재준비. 생성·전송·CPU 준비 비용 비교 |

## 데이터와 적용 경계

- 기존 typed control과 실제 적용 revision을 사용한다. UI 체크 상태를 실제 적용으로 간주하지 않는다. 지원 조건이 없는 기능은 사유와 함께 읽기 전용으로 표시한다.
- source별 최근 비교의 전후 원본 흐름만 제한적으로 보관한다. 과거 요청 전체에 상세 프레임을 복사하지 않는다. 상세 보관 한도와 유실 표시를 유지한다.
- 전후 1초 집계에는 혼합 revision, 불완전 구간, 준비되지 않은 GPU 값을 넣지 않는다. 원본 흐름도 frame/device/source/revision을 보존한다.
- 이벤트 ID는 프레임마다 달라질 수 있다. 전후 ID 차집합을 처리 흐름 변화로 해석하지 않는다. 단계·명령 종류·실제 연결의 변화와 작업량을 비교한다. 유실된 상세에서 보이지 않는 작업을 사라졌다고 단정하지 않는다.
- CPU 단계 시간은 중첩 또는 병렬 작업 시간을 포함할 수 있어 합계를 프레임 wall time으로 표시하지 않는다. GPU가 측정되지 않은 단계를 0으로 채우지 않는다.
- device 전체에 적용되는 정책은 Renderer/Model/raw source의 안전한 적용 시점과 revision을 맞춰야 한다. 다른 source의 비용을 현재 source의 비용으로 바꾸어 표시하지 않는다.
- 업로드 페이지의 신규 할당 수·재사용 수·신규 할당 바이트는 실제 획득이 발생한 원본 프레임에 별도로 기록한다. 이미 획득한 페이지 안에 추가로 넣는 slice를 페이지 재사용으로 세지 않는다. 이 계수는 논리 Upload나 제출·완료 계수, 단계별 전송 바이트에 더하지 않는다. 캐시 보유량은 장치 전체 gauge로 유지한다.
- barrier, validation, GPU 완료 확인, 제출된 자원의 보유는 정확성 조건이다. 비교를 위해 제거하지 않는다.

## 검증과 소유 경계

A는 common DTO/collector, Renderer·Model의 제어와 비교 경로, Canvas 공개 설정과 제어 등록을 담당한다. B는 RHI 업로드 정책과 backend 적용 경계, CanvasRenderer의 세 설정 소비 경로 및 Canvas native 검증을 담당한다. C는 기존 GUI 안의 기능 목록, 단계 비교, 전후 원본 흐름 표시를 담당한다. root는 설계·연결 검토·실제 native/UI 검증을 수행한다.

새 비활성 경로는 동일 입력의 출력 픽셀 또는 GPU payload가 유지되는지, 예상한 작업량만 바뀌는지 검증한다. Null/계약 테스트와 D3D12/Vulkan native 검증을 구분한다. 기존 upload·Renderer·Canvas·Model 검증 하네스를 재사용한다. 프로토콜/retention, late GPU 결과, 재접속, no-op·실패 적용도 확인한다.

실제 GUI에서 기능 전환, 단계별 값, 전후 원본 흐름, 가독성을 확인한다. 이는 기능 검증이다. 통제하지 않은 실시간 FPS 변화만으로 보편적인 성능 우열을 결론 내리지 않는다.
