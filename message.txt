※ 전사문에서 RH, RIH 등으로 인식된 표현은 문맥상 RHI로 통일했으며, 시험·수업·AI 서비스 등에 관한 사담은 제외했다.
1. 회의 핵심 결론
현재 프레임워크는 여러 기능을 갖추고 있지만, 개발에 참여한 팀원도 이를 활용해 새로운 예제를 만들기 어려울 정도로 사용 구조가 복잡하다는 문제가 확인됐다.
이에 따라 기능을 계속 추가하기보다 다음 순서로 개선하기로 했다.
1. SDL 예제를 참고해 필요한 샘플 목록을 정한다.
2. 팀원이 실제 프레임워크를 이용해 예제를 만들어 본다.
3. 예제 제작 과정에서 막히는 부분을 기록한다.
4. 문제가 문서, Graphics 계층, RHI, 백엔드 중 어디에 있는지 구분한다.
5. 부족한 기능은 추가하고 과도하거나 복잡한 구조는 정리한다.
즉, 문서상으로만 사용 흐름을 설계하는 것이 아니라 실제 사용 과정을 통해 프레임워크의 문제를 찾아 개선하는 방식으로 진행하기로 했다. 
2. 프레임워크의 가장 큰 문제
2-1. 팀원도 사용하기 어려운 복잡성
현재는 프레임워크 제작에 참여한 팀원조차 기존 코드를 바로 활용하기 어렵다. 이런 상태라면 외부 사용자가 프레임워크를 쉽게 사용하는 것은 더욱 어렵다는 의견이 나왔다.
따라서 팀원들이 정기적으로 직접 예제를 만들면서 다음 내용을 확인하기로 했다.
- 어떤 기능을 사용하려 했는가
- 어느 과정에서 막혔는가
- 필요한 클래스나 함수를 쉽게 찾을 수 있는가
- 반복되거나 지나치게 긴 코드가 있는가
- 사용법을 코드와 문서만 보고 이해할 수 있는가
- 백엔드를 변경해도 같은 결과가 나오는가
2-2. 백엔드별 구현 차이
Vulkan, Direct3D 12, Metal 등의 백엔드는 공통 RHI를 사용하므로 같은 명령에 동일하게 동작해야 한다. 그러나 윤훈이 추가한 일부 기능이 다른 백엔드에는 아직 반영되지 않아 실제 동작이 서로 다를 가능성이 있다고 확인됐다. 
공통 예제를 각 백엔드에서 실행하면서 다음을 검사하기로 했다.
- 같은 RHI 함수가 모든 백엔드에 구현돼 있는지
- 같은 입력에 같은 결과가 출력되는지
- 특정 백엔드에서만 자동 처리되는 설정이 있는지
- 특정 백엔드에서만 동작하지 않는 기능이 있는지
- 새 기능이 모든 백엔드에 반영됐는지
3. 예제 구성 방향
SDL의 예제 구조를 참고해 처음부터 복잡한 모델이나 렌더링 기술을 다루기보다, 작은 기능부터 결과를 눈으로 확인할 수 있는 예제를 만드는 방향으로 논의됐다.
3-1. 기본 예제 후보
- 창 및 렌더링 환경 초기화
- 카메라 설정
- 점 그리기
- 선 그리기
- 사각형 그리기 및 채우기
- 원과 원호 그리기
- 배경색 및 오브젝트 색상 설정
- 그라데이션 표현
- 이미지 및 텍스처 출력
- 이미지 포맷별 출력
- 뷰포트 설정
- 화면 영역 분할
- Clip Rect 적용
- 블렌딩
- Geometry 및 버텍스 기반 출력
- 인스턴스 드로우
- 텍스트 출력
기본 도형 예제는 단순한 학습용 기능이면서도 화면에 바로 결과가 표시되기 때문에, 프레임워크의 초기화와 렌더링 흐름을 확인하는 데 유용하다고 판단했다. 
3-2. 기능별 예제 분리
하나의 예제에 모든 기능을 넣기보다 큰 주제별로 나누고, 그 안에서 기능을 단계적으로 설명하기로 했다.
예를 들어 이미지 관련 예제는 다음과 같이 구성할 수 있다.
1. 기본 이미지 출력
2. 이미지 색상 변경
3. 그라데이션 적용
4. 포맷별 이미지 출력
5. 텍스처 색상 모드 변경
6. 블렌딩 적용
이러한 구성은 사용자가 자신에게 필요한 기능만 선택해 확인할 수 있고, 각 API가 어떤 결과를 만드는지도 쉽게 파악할 수 있다는 장점이 있다. 
3-3. 뷰포트와 화면 분할
뷰포트는 단순히 창 전체에 렌더링하는 기능뿐 아니라, 하나의 창 안을 여러 영역으로 나누어 각각 다른 결과를 출력하는 데 사용할 수 있다.
활용 예시는 다음과 같다.
- 분할 화면
- 미니맵
- 에디터의 여러 뷰
- 특정 영역만 렌더링
- 서로 다른 카메라 결과 출력
따라서 뷰포트와 Clip Rect도 사용자가 쉽게 접근할 수 있는 기능으로 제공할 필요가 있다고 논의됐다. 
4. 하이레벨 Graphics와 로우레벨 RHI 구분
예제는 크게 하이레벨 Graphics 예제와 로우레벨 RHI 예제로 구분하기로 했다.
하이레벨 Graphics 예제
일반 사용자가 프레임워크를 쉽게 사용하는 방법을 보여주는 예제다.
- 창과 카메라 초기화
- 오브젝트 생성
- 이미지와 텍스처 출력
- 기본 도형 출력
- 메시와 머티리얼 사용
- 장면 구성
- 색상, 블렌딩, 뷰포트 설정
로우레벨 RHI 예제
그래픽스 내부 구조나 성능을 직접 제어하려는 사용자를 위한 예제다.
- 셰이더 직접 제어
- 렌더 패스 구성
- 렌더 그래프 조작
- 파이프라인 설정
- 버퍼 및 텍스처 직접 관리
- 성능 관련 설정
- 백엔드에 가까운 명령 처리
Graphics 계층은 RHI와 별개의 기능을 임의로 만드는 계층이 아니라, 여러 RHI 명령을 조합해 더 쉽게 사용할 수 있도록 제공하는 상위 계층이어야 한다는 방향으로 정리됐다.  
5. 예제 코드 간소화
현재 RHI와 직접 소통하는 방식으로 예제를 작성하면, 중간 계층에서 처리해야 할 설정까지 예제 코드로 올라와 코드가 지나치게 길어지는 문제가 있다.
회의에서 언급된 비교는 다음과 같다.
- 단순화한 예제: 약 30줄
- RHI에 직접 접근한 예제: 전체 약 180줄
목표는 단순히 줄 수를 줄이는 것이 아니라, 반복되는 초기화와 공통 처리를 재사용 가능한 계층으로 옮기고 예제에는 실제로 설명하려는 기능만 남기는 것이다. 
다만 예제를 지나치게 축약해 내부 동작을 전혀 볼 수 없게 만들기보다는, 사용자가 조명 설정이나 장면 구성 흐름을 읽을 수 있는 정도의 코드는 남기는 것이 적절하다고 판단했다. 
예제를 작성한 뒤 다음 항목을 판별하기로 했다.
- RHI에 부족한 기능
- Graphics 계층에서 감춰야 할 반복 처리
- 사용자가 직접 설정할 필요가 없는 항목
- 과도하게 외부에 노출된 RHI 기능
- 예제에만 존재하고 재사용되지 않는 코드
6. README와 API 문서 필요성
현재 README와 API 문서가 충분하지 않아 사용자가 다음 내용을 확인하기 어렵다는 문제가 제기됐다.
- 각 함수의 역할
- 함수 호출 순서
- 필요한 입력값
- 함수 실행 결과
- Graphics와 RHI 중 어느 계층을 사용해야 하는지
- 기본적인 예제 코드
특히 함수별 역할과 사용 예제가 포함된 API 문서가 기능을 가장 빠르게 찾아볼 수 있는 형태라는 의견이 나왔다. 현재는 문서가 부족해 일부 사용 흐름을 추측해야 하는 상태다. 
또한 초기 개발 당시와 비교해 프레임워크의 동작 방식이 달라진 부분이 있으므로, 기존 팀원도 현재 사용법을 헷갈릴 수 있다. 변경된 사용 흐름을 설명하는 README가 필요하다는 결론이다. 
7. 브랜치 병합 방향
분리된 기능과 변경사항을 각 브랜치에 계속 유지하기보다, 현재 시점에서는 브랜치를 통합해야 한다는 데 의견이 모였다.
병합은 다음 방향으로 진행하기로 했다.
- 현재 변경사항을 통합 브랜치에 모은다.
- 필요하면 main-clean을 기준으로 리베이스한다.
- 중복된 프로토타입과 파일을 정리한다.
- 최종적으로 PR을 생성한다.
- 커밋 기록이 지나치게 복잡하면 Squash를 사용한다.
- 커밋 기록의 완벽한 정리보다 실제 기능 통합을 우선한다.
윤훈이 병합 작업을 담당하며, 이미 변경사항을 한 번에 병합할 수 있도록 어느 정도 준비해 놓은 상태라고 설명했다.  
8. 로그와 CI 도입
8-1. 로그
로그는 단순히 오류 발생 여부만 보여주는 것이 아니라 최소한 다음 정보를 제공해야 한다.
- 어떤 오류가 발생했는가
- 어느 위치에서 발생했는가
- 어떤 처리 과정에서 문제가 생겼는가
로그 기능은 나중에 별도 작업으로 미루기보다, 예제 제작과 백엔드 검증을 진행하면서 함께 구축하는 것이 적절하다고 판단했다. 
8-2. CI 자동 검증
코드를 올릴 때 자동으로 검사하는 CI도 도입하기로 했다.
검토할 수 있는 항목은 다음과 같다.
- 빌드 실패 여부
- 필수 구현 누락
- 백엔드별 동작 차이
- 백엔드 내부에 임의로 추가된 설정
- 공통 규칙 위반
- 기본 샘플 실행 실패
구체적인 검사 항목과 방법은 아직 확정되지 않았지만, 윤훈이 브랜치 병합과 함께 CI 구성을 담당하기로 했다. 
9. 현재 구현 상태와 이후 기능
회의에서 확인된 현재 구현 범위는 모델 스키닝까지다.
이후 추가하거나 검토할 기능은 다음과 같다.
- 멀티 렌더링 또는 다중 렌더 구조
- 렌더 그래프
- 멀티스레딩
- 로그
- 프로파일러 확인 및 연동
- 장기적인 레이트레이싱 지원
현재 렌더링 처리는 싱글 스레딩 기반이므로 멀티스레딩 기능이 필요하다는 의견이 나왔다. 레이트레이싱은 현재 구조에서 아직 거리가 먼 후순위 기능으로 평가됐다. 
프로파일러의 현재 구현 상태는 참석자들이 정확히 파악하지 못하고 있으므로 정준혁에게 확인하기로 했다.

11. 다음 회의 진행 방식
다음 수요일에는 완성된 설계안을 발표하기보다 현재 프로젝트 코드를 직접 보면서 예제를 만들어 보기로 했다.
진행 순서는 다음과 같다.
1. 참여자들이 현재 코드를 간단히 훑어본다.
2. 기존 프로젝트를 기준으로 처음부터 예제를 만들어 본다.
3. 창 초기화부터 실제 렌더링까지 진행한다.
4. 작업이 막히는 지점을 기록한다.
5. 막힌 원인을 함께 분석한다.
6. 문서, API, RHI, 백엔드 중 어느 부분의 문제인지 구분한다.
7. 각 백엔드에서 동작하지 않는 기능을 수정한다.
완전히 준비된 상태에서 작업하기보다, 실제 사용자가 겪을 수 있는 혼란을 확인하기 위해 현재 코드만 보고 작업을 진행하는 방식으로 결정됐다. 다만 최소한 코드 구조는 미리 한 번 확인하고 오는 것이 좋다는 의견도 반영됐다. 
다음 회의는 수요일에 진행하기로 했다.
